# 사용자 의도 파악

* 목표 기능
  `goal=AI가 tmux 또는 tmux-backed 세션을 직접 제어`하고, `log_capture=1`, `process_restart=1`, `interactive_debug=1` 상태로 앱/서버를 붙잡은 채 디버깅할 수 있게 해 주는 오픈소스 repo를 찾는 것이다.

* 필수 요구사항
  `skill_surface=1`, `session_create=1`, `output_capture=1`, `send_input=1`, `stop_or_restart_path=1`, `module_visible=1` 이어야 한다.

* 선택 요구사항
  `human_handoff=1`, `wait_or_sync_helper=1`, `multi_session=1`, `maint_signal>=medium`, `tests_or_examples=1` 이면 가점이다.

* 제외 조건
  `mcp_only=1 && skill_surface=0`, `agent_specific_scope=1 && generic_debug_fit<0.7`, `module_hidden=1`, `runtime_path_opaque=1` 이면 제외 또는 보류한다.

* 성공 판정 기준
  `accept = skill_surface && (tmux_raw || tmux_backed) && log_capture && restart_path && module_visible`.

# 라우팅 / 루프 진입 전의 Task

* 사용자 요구를 검색 가능한 키워드와 검증 가능한 기능 단위로 정규화
  정규화 키워드는 `tmux skill`, `AI agent skill`, `log capture`, `restart server`, `interactive debugger`, `send-keys`, `capture-pane`, `wait-for`, `dev server`, `tmux-backed session` 으로 잡았다.

* GitHub 검색 쿼리 생성
  사용한 대표 쿼리는 `site:github.com tmux AI skill debug logs restart server`, `site:github.com "tmux" "SKILL.md"`, `site:github.com tmux-backed agent skill dev server`, `site:github.com tmux agent lifecycle monitor stop start` 였다.

* repo 후보 수집
  `C1=mitsuhiko/agent-stuff` 는 `skills/tmux/SKILL.md` 와 `scripts/` 를 가진 literal tmux skill 후보다. repo는 agent용 커맨드/skills 모음이며 tmux skill이 별도 모듈로 존재하고, 현재 별 1.5k 수준의 유지보수 신호가 있다. ([GitHub][1])
  `C2=EliasOenal/term-cli` 는 tmux-backed 세션을 AI가 다루게 하는 single-file Python 도구이며, skill 폴더를 함께 제공하고 dev server, debugger, log watcher 사례를 명시한다. 별 50, “680+ tests” 신호가 있다. ([GitHub][2])
  `C3=Dwsy/agent` 는 monorepo 안에 `skills/tmux` 를 포함하고, CLI/TUI/API 레벨의 tmux 세션 관리 기능을 제공한다. 별 25, Bun/PI Agent 전제가 있다. ([GitHub][3])
  `C4=fractalmind-ai/agent-manager-skill` 은 tmux+Python 기반 agent lifecycle manager 로 `start/status/monitor/stop/assign/schedule` 을 제공하지만, 기본 스코프가 `agents/` 아래 employee agent 운용이다. 별 18이다. ([GitHub][4])
  `C5=anhvth/mcp-tmux-operator` 는 tmux session 관리 MCP 서버지만 skill 자체는 아니고, 현재 별 0이라 maintenance signal 이 약하다. ([GitHub][5])

* repo 초기 점수화
  `score(C1)=0.88`, `score(C2)=0.81`, `score(C3)=0.81`, `score(C4)=0.73`, `score(C5)=0.57` 로 시작했다.
  점수축은 `literal_skill_match`, `debug_workflow_match`, `module_visibility`, `runtime_surface`, `maintenance_signal` 이다.

* 검증 전략 초기화
  1차는 `literal tmux skill` 우선, 2차는 `실제 로그/재시작 디버깅 워크플로우` 우선으로 잡았다. 그래서 `C1 -> C2 -> C3 -> C4 -> C5` 순으로 L1 진입했다.

# 라우팅 규칙

## [R1-001] Repo 적합성 라우팅

* parent scope: `L1-001`
* 평가 변수
  `v_feature_fit`, `v_module_visibility`, `v_runtime_surface`, `v_maintenance`
* 판정식
  `Pass = v_feature_fit>=0.85 && v_module_visibility>=0.70 && v_runtime_surface>=0.60 && v_maintenance>=0.40`
  `Hold = v_feature_fit>=0.65 && v_module_visibility>=0.60 && v_runtime_surface>=0.45`

* parent scope: `L2-*`
* 평가 변수
  `v_function_centrality`, `v_entrypoint`, `v_examples_or_tests`, `v_dep_complexity`
* 판정식
  `Core = v_function_centrality>=0.80 && (v_entrypoint==1 || v_examples_or_tests==1)`
  `Supporting = v_function_centrality>=0.45`
  `Irrelevant = else`

## [R3-001] 코드 양 / 실행 가능성 라우팅

* parent scope: `L2-*`
* 평가 변수

* 판정식

  `Static-first = v_entrypoint==0 || v_env_ready==0`

## [R4-001] 정합성 / fallback 라우팅

* 평가 변수

  `Retry with other module in same repo = v_intent_alignment>=0.70 && v_mismatch_severity>0.30 && same_repo_alt_exists==1`
  `Retry with another repo = v_intent_alignment<0.70 || same_repo_alt_exhausted==1`

# 루프

## [L1-001] Repo 후보 탐색 루프

* parent scope: `root`

* 내부 Task: `select_repo_by_score`, `inspect_docs_and_tree`, `apply_R1-001`

* 진입 조건: `repo_candidate_count>0`

* 탈출 조건: `accepted_repo_count>=1 || remaining_repo_count==0`

* 실행 trace
  `iter=1 repo=C1(mitsuhiko/agent-stuff)` → `R1=Pass`
  이유: literal `skills/tmux` 모듈, helper scripts 존재, 유지보수 신호 강함. ([GitHub][6])
  `iter=2 repo=C2(EliasOenal/term-cli)` 는 C1 내부 mismatch 후 재진입하여 `R1=Pass`
  이유: tmux-backed 이지만 skill 포함, dev-server/debugger/log-watcher 워크플로우가 직접적으로 드러난다. ([GitHub][2])
  `iter=3 repo=C3(Dwsy/agent)` → `R1=Hold`
  이유: 기능은 강하지만 Bun + Pi Agent monorepo 진입 비용이 높다. ([GitHub][3])
  `iter=4 repo=C4(fractalmind-ai/agent-manager-skill)` → `R1=Hold`
  이유: start/monitor/assign/schedule 는 강하지만 범위가 generic app debugging 보다 employee-agent orchestration 쪽에 치우친다. ([GitHub][7])
  `iter=5 repo=C5(anhvth/mcp-tmux-operator)` → `R1=Reject`
  이유: skill surface 부재, maintenance signal 약함. ([GitHub][5])

## [L2-001] Repo 내부 module 검증 루프

* parent scope: `L1-001:C1`

* 내부 Task: `extract_modules`, `apply_R2-001`, `apply_R3-001`

* 진입 조건: `repo_state=Pass`

* 탈출 조건: `coherent_core_module_found==1 || module_candidate_count==0`

* 실행 trace
  `M1=skills/tmux/SKILL.md` → `R2=Core`, `R3=Static-first`
  이유: private socket, `send-keys`, `capture-pane`, `kill-session`, monitoring command 출력, interactive tool recipe 가 모두 skill 문서 안에 있다. ([GitHub][8])
  `M2=skills/tmux/scripts/wait-for-text.sh` → `R2=Core`, `R3=Dynamic-first`
  이유: pane polling 으로 prompt/text 동기화를 담당한다. ([GitHub][8])
  `M3=skills/tmux/scripts/find-sessions.sh` → `R2=Supporting`, `R3=Dynamic-first`
  이유: socket/path/all scan 으로 세션 찾기와 보조 진단을 담당한다. ([GitHub][9])

* 불일치 탐지
  `socket_flag_consistency=0`
  같은 `SOCKET` 변수에 대해 quickstart/cleanup 은 `tmux -S "$SOCKET"` 를 쓰는데, send/watch 예시는 `tmux -L "$SOCKET"` 로 바뀐다. `-S` 는 socket path, `-L` 은 socket name 이라 문서 일관성이 깨진다. ([GitHub][10])
  `helper_socket_propagation=0`
  `wait-for-text.sh` 는 옵션 목록에 `-S/-L` 이 없고 내부 호출도 plain `tmux capture-pane` 이라, skill 문서가 권장하는 isolated private socket 흐름을 그대로 따라가지 못한다. ([GitHub][11])

* R4 결과
  `R4=Retry with other module in same repo` 후 `same_repo_alt_exhausted=1`
  `find-sessions.sh` 는 `-S/-L` 을 모두 지원해 보조 진단에는 좋았지만, prompt wait helper 의 socket gap 을 메우지 못했다. 그래서 최종적으로 `Retry with another repo` 로 승격했다. ([GitHub][9])

## [L3-001] 실행 / 트러블슈팅 루프

* parent scope: `L2-001:M2(wait-for-text.sh)`

* 내부 Task: `env_check`, `run`, `debug_error`, `rerun`, `verify_output`

* 진입 조건: `route_mode=Dynamic-first`

* 탈출 조건: `module_behavior_verified==1 || retry_budget==0`

* 로컬 검증 trace
  `step=1` `tmux_binary=0` → stderr=`tmux not found in PATH` 로 즉시 실패.
  `step=2` `shim_tmux=1` 로 재시도 → success path 검증: 패턴 출현 후 `exit_code=0`.
  `step=3` `shim_tmux=1` 로 timeout path 검증 → 마지막 pane dump 를 stderr 에 남기고 `exit_code=1`.
  결론: shell helper 자체의 성공/실패 계약은 명확했다. 다만 `real_tmux_e2e=0` 이라 socket mismatch 문제는 여전히 남았다.

  결론: supporting module 로는 충분히 건전했다.

# 최종 출력

* 추천 repo
  `EliasOenal/term-cli`

* 추천 핵심 module
  `term-cli` 실행 파일 + `skills/term-cli/SKILL.md`

* 검증 근거
  이 repo는 tmux-backed detached session 을 AI가 다루도록 설계되어 있고, README/skill 문서에 dev server 예제를 직접 넣어 `start -> run "npm run dev" -> wait-idle -> capture -> send-key C-c -> kill` 흐름을 보여 준다. 이는 사용자가 말한 “로그를 보고 서버를 껐다 켰다 하며 디버깅” 요구와 거의 일치한다. ([GitHub][2])
  CLI 표면도 충분히 넓다. `capture`, `wait`, `wait-idle`, `wait-for`, `pipe-log`, `status`, `send-key`, `send-text`, `upload/download`, `request*` 를 제공해 단순 tmux 조작보다 실제 디버깅 루프에 가깝다. ([GitHub][2])
  skill 문서는 `wait-for` 의 함정까지 짚는다. echo 된 명령 문자열 때문에 패턴이 즉시 매치되는 문제를 경고하고, `npm run dev` 뒤에는 `"Listening on port"` 같은 프로그램 출력 기준으로 기다리라고 가이드한다. 이건 agent 디버깅에서 매우 중요한 정합성 포인트다. ([GitHub][13])
  구현 면에서도 single-file Python, tmux 외 무거운 런타임 의존성 없음, skill 동봉, 680+ tests 라는 점이 운영 안정성 신호로 충분했다. ([GitHub][2])

* 발견한 불일치
  이 repo의 불일치는 `raw tmux skill` 이 아니라 `tmux-backed abstraction` 이라는 점이다. 즉, “AI에게 tmux 명령 자체를 직접 주입”하려는 목적이라면 literal match 는 `mitsuhiko/agent-stuff` 나 `Dwsy/agent` 쪽이 더 높다. 다만 실제 디버깅 워크플로우 일관성은 `term-cli` 가 더 좋았다. ([GitHub][8])
  추가로, 현재 sandbox 에 `tmux` 바이너리가 없어서 real tmux e2e smoke 는 못 했다. 그래서 최종 판정은 `docs+entrypoint+error-contract` 기반 accept 이다. ([GitHub][12])

* 같은 repo 내 대안 module
  `term-assist`
  비밀번호, MFA, 수동 개입, read-only attach, lock/unlock 이 필요한 경우에는 `term-cli` 단독보다 `term-assist` 를 같이 쓰는 편이 더 안전하다. repo 문서에 `term-assist list/attach/done/detach/start/kill/lock/unlock` 흐름이 정리돼 있다. ([GitHub][2])

* 필요 시 다음 repo로 넘어간 이유
  `mitsuhiko/agent-stuff` 는 literal tmux skill 이라 1순위로 들어갔지만, `-S` 와 `-L` 혼용, `wait-for-text.sh` 의 socket 옵션 부재 때문에 isolated-socket 디버깅 루프 정합성이 깨졌다. 같은 repo 안의 `find-sessions.sh` 는 괜찮았지만 핵심 wait helper 문제를 해결하지 못해 다음 repo로 넘겼다. ([GitHub][8])
  `Dwsy/agent` 는 `create/send/capture/kill/cleanup/attach/sync` 와 `service` 카테고리까지 있어 차선책으로 강력했지만, Bun + Pi Agent monorepo 진입 비용 때문에 이번 요구에서는 보류했다. ([GitHub][14])
  `fractalmind-ai/agent-manager-skill` 은 `start/status/monitor/stop/assign/schedule/heartbeat` 가 강점이지만, generic app/server debugging 보다는 employee-agent orchestration 에 더 가깝다. ([GitHub][7])

실무적으로는, **literal tmux skill이 꼭 필요하면 `mitsuhiko/agent-stuff`를 수정 전제로 쓰고, 바로 디버깅 생산성을 원하면 `EliasOenal/term-cli`를 고르는 것이 가장 낫다.**
