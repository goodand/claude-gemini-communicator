# tmux 제어 스킬 구현을 위한 상세 체크리스트

이 체크리스트는 에이전트가 **tmux**를 안전하게 제어할 수 있도록 하는 스킬(또는 MCP 모듈)을 구현하는 전체 과정을 단계별로 설명합니다. 단계는 매우 세분화되어 있으며, 계획‑설계부터 설치, 기능 구현, 테스트, 보안, 문서화까지 모두 포함합니다. 이 목록을 참고하여 환경과 요구사항에 맞게 수정하거나 확장할 수 있습니다.

## 1. 요구사항 분석 및 설계 준비

1. **사용 사례 정의**
   - 에이전트가 tmux를 어떤 목적으로 제어하는지 명확히 합니다. 예를 들어, 여러 코딩 세션을 관리하는 **세션 매니저**인지, 단일 세션 내에서 명령을 실행하는 **단순 제어 스킬**인지 결정합니다.
   - 원격 서버에서 tmux를 제어해야 하는지(SSH 경유), 로컬 환경만 대상인지 구분합니다.
   - 결과를 어떻게 반환할 것인지(즉시 출력, 캡처 후 후속 처리, 스트리밍 등) 정의합니다.

2. **기존 오픈소스 프로젝트 검토**
   - 에이전트 운영형 세션 관리가 필요하면 `asheshgoplani/agent-deck`를, 에이전트가 직접 tmux 명령을 호출해야 하는 경우 `k8ika0s/mcp-tmux` 또는 `bnomei/tmux-mcp` 등을 참고합니다. 스킬 형태가 중요한 경우 `Dwsy/agent`의 tmux Skill 구조를 검토합니다.
   - 각 프로젝트의 라이선스, 사용 언어(Node, TypeScript, Python, Rust 등), 기능 범위, 유지보수 상태를 확인합니다.

3. **기술 스택 및 개발 언어 선택**
   - 에이전트 플랫폼(예: Claude API, 맞춤형 OpenAI 에이전트)에서 호출 가능한 언어와 모듈 포맷을 고려하여 Node.js, TypeScript, Python, Rust 중 적합한 스택을 결정합니다.
   - tmux 제어는 결국 터미널 명령 실행이므로, 언어에서 **외부 프로세스 실행**과 **결과 캡처** 기능을 지원해야 합니다. 예시: `child_process.exec`(Node), `subprocess`(Python), `Command` 구조체(Rust 등).

4. **보안 요구사항 정리**
   - tmux 세션을 통해 실행될 명령이 시스템에 미치는 영향을 평가하고, **파괴적 작업(kill, 서버 종료)**에는 추가 확인을 요구하도록 설계합니다.
   - 에이전트와 사람 사용자의 협업을 염두에 두고 **로그 기록**(명령, 시간, 발신자)과 **감사 추적**을 구현해야 합니다.
   - 운영 환경과 완전히 분리된 **에이전트 전용 tmux 소켓**을 사용하는 방안 검토합니다.

5. **테스트 계획 수립**
   - 기능별로 세션 생성, 윈도우 추가, 패널 분할, 명령 전달, 출력 캡처, 레이아웃 저장/복구, 세션 종료 등을 검사하는 테스트 케이스를 설계합니다.
   - 정상적인 명령과 예외 상황(대상 세션 없음, 잘못된 명령, 권한 부족 등)을 모두 포함합니다.

## 2. 개발 환경 설정

1. **종속 패키지 설치**
   - tmux가 설치되어 있는지 확인합니다. `tmux -V`로 버전을 확인하고, 지원하려는 최소 버전 이상인지 검증합니다. **tmux 설치가 없으면** 패키지 매니저로 설치합니다.
   - 선택한 프로그래밍 언어의 환경을 준비합니다(Node.js ≥ v18, Python ≥ 3.8, Rust ≥ 1.67 등). 프로젝트 리포지터리 구조를 설정하고 패키지 관리자(`npm`, `pip`, `cargo` 등)를 초기화합니다.

2. **전용 tmux 소켓 준비**
   - 안전을 위해 스킬이 사용할 tmux 서버를 일반 사용자 세션과 분리합니다. 예를 들어 `/tmp/agent-tmux-socket` 같은 경로에 소켓을 지정하여 세션을 생성합니다. 이를 통해 실수로 메인 터미널 세션을 종료하거나 오염시키는 것을 방지합니다.
   - 초기화 스크립트에서 `tmux -S /tmp/agent-tmux-socket new-session -d -s bootstrap`와 같이 서버를 백그라운드에서 실행시키고, 이후 모든 명령에 `-S /tmp/agent-tmux-socket` 플래그를 포함하는 방식을 사용할 수 있습니다.

3. **라이브러리/SDK 설정**
   - Node.js/TypeScript라면 `execa` 또는 `node-pty` 같이 터미널 명령 실행과 입출력 파이프 처리에 적합한 라이브러리를 설치합니다.
   - Python이라면 `subprocess.Popen` 또는 `pexpect`를 활용해 tmux 명령을 실행하고 결과를 실시간 스트림으로 받을 수 있습니다.
   - Rust라면 `std::process::Command` 또는 `tokio::process::Command`를 비동기로 사용하여 tmux를 호출합니다.

4. **프로젝트 구조 정의**
   - 코어 로직과 API 레이어를 분리합니다. 예를 들어 `src/tmuxController.ts`(tmux 명령 실행), `src/skill.ts`(에이전트로부터 들어오는 요청을 받아 tmuxController 함수를 호출하고 결과를 반환)처럼 구성합니다.
   - 유형 안전성을 위해 TypeScript 인터페이스 또는 Python 데이터 클래스 등을 사용해 스킬의 입력/출력 스키마를 정의합니다.

## 3. 기본 tmux 명령 학습 및 함수 설계

이 단계에서는 tmux의 기본 명령을 이해하고, 각 명령을 래핑하는 함수를 설계합니다. GitHub tmux 위키의 설명을 참고하여 실제 동작을 확인합니다.

1. **세션 생성과 확인**
   - `new-session`(`new`) 명령을 사용하면 tmux 세션을 새로 만들 수 있습니다. 인자를 주지 않으면 새로운 세션을 생성하고 자동으로 붙습니다【436416818119683†L373-L384】. 예를 들어:

     ```bash
     tmux new -S /tmp/agent-sock -smysession
     ```

   - `new-session`에 `-s` 플래그를 사용하면 세션 이름을 지정할 수 있습니다【436416818119683†L386-L390】. `-n`은 첫 번째 윈도우의 이름을 정합니다【436416818119683†L401-L404】.
   - 세션 목록은 `list-sessions`(`ls`) 명령으로 확인합니다. 결과는 세션 이름, 창 수, 생성 시각 등의 형태로 출력됩니다【436416818119683†L555-L563】.

2. **윈도우 관리**
   - `new-window`(`neww`) 명령으로 세션에 새 윈도우를 추가할 수 있습니다. `C-b c`와 동일한 동작이며, `-d` 플래그로 새 윈도우를 현재 윈도우로 전환하지 않고, `-n` 플래그로 이름을 지정할 수 있습니다【436416818119683†L573-L596】. 
   - 윈도우 목록은 `list-windows`(`lsw`) 명령 또는 `display-message -p '#{window_index}:#{window_name}'` 식의 포맷을 사용하여 가져올 수 있습니다.
   - 윈도우를 종료하려면 `kill-window`를 사용합니다. 세션 내 윈도우가 모두 사라지면 세션이 자동으로 종료될 수 있으므로 주의합니다.

3. **패널(창 분할) 관리**
   - `split-window` 명령을 통해 현재 윈도우를 분할하여 새 패널을 만듭니다. 기본 키 바인딩으로 `C-b %`(수평 분할), `C-b "`(수직 분할)과 같으며 `-h`(수평) 또는 `-v`(수직) 플래그를 사용할 수 있습니다【436416818119683†L612-L637】.
   - `split-window`의 `-d` 플래그는 활성 패널을 변경하지 않고 분할만 수행하고, `-f` 플래그는 창 전체 폭/높이를 사용하여 분할합니다【436416818119683†L626-L634】.
   - 현재 활성 패널을 이동하거나 선택하는 명령(`select-pane`)도 래핑할 수 있으며, 패널 ID는 `#{pane_id}` 포맷으로 조회합니다.

4. **키 입력 전송**
   - 에이전트가 프로그램에 명령을 보낼 때는 `send-keys` 명령을 사용합니다. 이 명령은 대상 패널에 키 입력을 전달합니다【261256137316099†L907-L923】. tmux는 인자를 개별 키 이름으로 인식하려 시도하고, 이름에 해당하지 않는 문자열은 그대로 전송합니다. 예를 들어 `send hello Enter`는 `hello` 문자열을 치고 Enter를 누르는 동작을 수행합니다【261256137316099†L907-L917】.
   - 키 이름으로 사용되는 특수 키는 `F1`, `C-F2`(Ctrl+F2) 등이며, `-l` 플래그를 사용하면 인자를 키로 해석하지 않고 문자열 그대로 전송합니다【261256137316099†L923-L927】.
   - 패널 지정은 `-t <session>:<window>.<pane>` 형식으로 합니다. 스킬 내부에서는 패널 ID를 추적하여 정확하게 타겟팅하도록 합니다.

5. **출력 캡처**
   - 프로그램의 출력을 에이전트가 읽어야 할 때는 `capture-pane` 명령을 사용합니다. `-p` 플래그를 주면 캡처된 내용을 표준 출력으로 반환합니다【261256137316099†L930-L943】. 
   - `-S`와 `-E` 플래그를 이용해 캡처 영역의 시작 줄과 끝 줄을 지정합니다【261256137316099†L938-L942】. `-`를 사용하면 히스토리 전체를 포함합니다【261256137316099†L938-L943】.
   - `-e`, `-C`, `-N`, `-J` 플래그로 색상 코드, 비인쇄 문자 이스케이프, 끝 공백 유지, 줄 이어 붙이기 등을 설정할 수 있습니다【261256137316099†L947-L953】. 스킬의 요구에 맞게 필요한 플래그를 선택합니다.

6. **세션/윈도우/패널 종료**
   - `kill-session`, `kill-window`, `kill-pane` 등의 명령을 통해 각각 종료할 수 있습니다. 이러한 파괴적 명령은 에이전트 사용 시 큰 영향을 미칠 수 있으므로 **필수로 사용자 확인(confirm)** 절차를 구현합니다.
   - `kill-server`는 모든 세션을 중단하고 tmux 서버를 종료합니다【436416818119683†L567-L571】. 일반적으로 사용하지 말고, 서버 재시작이 필요할 때만 옵션으로 제공합니다.

7. **레イ아웃 및 상태 관리**
   - `list-panes` 명령으로 각 패널의 ID, 제목, 크기 등의 메타데이터를 조회하여 레이아웃을 재구성할 때 사용합니다.
   - 레이아웃 저장과 복원을 위해 `layout save`/`layout apply` 기능을 자체적으로 구현할 수 있습니다. 예를 들어 `tmux list-windows -F '#{window_index} #{window_layout}'`를 저장하고, 나중에 `select-layout` 명령으로 적용합니다.

## 4. 스킬 함수 구현 단계

각 tmux 명령을 스킬 또는 모듈의 메서드로 래핑하는 단계입니다. 아래는 함수 설계 시 따라야 할 구체적인 절차입니다.

1. **공통 유틸리티 작성**
   - 모든 tmux 호출에 대해 공통적으로 적용되는 소켓 플래그(예: `-S /tmp/agent-sock`)와 타임아웃, 환경 변수를 설정하는 함수(`buildCommandArgs`)를 작성합니다.
   - 실행 함수(`runTmuxCommand`)를 만들어 명령어 배열과 옵션을 받아 tmux 프로세스를 실행하고, 표준 출력/표준 오류를 캡처해 반환합니다.
   - 오류 발생 시(종료 코드 ≠ 0) 적절히 예외를 발생시키거나 표준 오류 메시지와 함께 결과를 반환합니다.

2. **세션 관리 함수**
   - `createSession(name: string, command?: string, windowName?: string): SessionInfo`
     1. `name`이 이미 존재하는지 `tmux has-session -t name`으로 검사합니다. 존재하면 오류 또는 기존 세션에 붙을지 옵션을 제공합니다.
     2. 존재하지 않으면 `tmux new-session -d -s name`을 실행하여 백그라운드 세션을 생성합니다. 필요한 경우 `-n` 플래그로 윈도우 이름, 추가 인자로 명령을 전달합니다.
     3. 실행 후 `listSessions()`를 호출하여 생성된 세션 정보(윈도우 개수, ID 등)를 반환합니다.
   - `listSessions(): SessionInfo[]`
     1. `tmux ls -F '#S #{session_id} #{session_windows} #{session_created}'` 등을 실행하여 파싱 가능한 포맷으로 얻습니다.
     2. 문자열을 분할하여 세션 배열을 반환합니다.
   - `attachSession(name: string): void`
     1. 필요 시 `tmux attach-session -t name`을 호출하여 사용자가 실제 터미널에서 세션에 붙을 수 있게 합니다. 에이전트가 직접 인터랙티브 세션에 붙지 않는 설계라면 구현하지 않아도 됩니다.
   - `killSession(name: string, confirm: boolean): void`
     1. `confirm`이 `true`일 때만 `tmux kill-session -t name`을 실행합니다. 사용자에게 확인을 받지 않았다면 오류 메시지로 처리합니다.

3. **윈도우 관리 함수**
   - `createWindow(session: string, name?: string, command?: string): WindowInfo`
     1. `tmux new-window -t session -P -F '#{window_id} #{window_index}' -n name command...`을 실행해 결과 포맷을 파싱합니다. `-P` 플래그는 출력 포맷을 그대로 반환합니다.
   - `listWindows(session: string): WindowInfo[]`
     1. `tmux list-windows -t session -F '#{window_id} #{window_index} #{window_name} #{window_active}'`를 실행하고, 각 윈도우 정보를 구조체로 만듭니다.
   - `killWindow(session: string, windowId: string, confirm: boolean): void`
     1. `confirm` 확인 후 `tmux kill-window -t windowId`를 실행합니다.

4. **패널 관리 함수**
   - `splitPane(targetPane: string, direction: 'horizontal' | 'vertical', command?: string, stayCurrent?: boolean): PaneInfo`
     1. `direction`에 따라 `-h` 또는 `-v` 플래그를 결정합니다.
     2. `stayCurrent`가 `true`이면 `-d` 플래그를 추가하여 현재 패널을 유지합니다.
     3. 명령이 있다면 인자로 전달하여 새 패널에서 실행합니다. 
     4. `-P -F '#{pane_id} #{pane_width} #{pane_height}'`를 함께 사용해 새 패널의 정보를 얻습니다.
   - `listPanes(target: string): PaneInfo[]`
     1. `target`은 `<session>:<window>` 형식입니다. `tmux list-panes -t target -F '#{pane_id} #{pane_index} #{pane_active} #{pane_title}'`로 정보를 가져옵니다.
   - `killPane(paneId: string, confirm: boolean): void`
     1. `tmux kill-pane -t paneId`를 호출합니다. 확인 절차는 동일합니다.

5. **키 입력 및 명령 실행 함수**
   - `sendKeys(paneId: string, keys: string[], literal?: boolean): void`
     1. `keys` 배열을 공백으로 join하여 `tmux send-keys -t paneId` 뒤에 추가합니다. 키 이름 판별이 필요 없도록 할 경우 `literal`이 `true`이면 `-l` 플래그를 앞에 추가합니다【261256137316099†L923-L927】.
     2. 대부분의 명령을 실행하려면 마지막에 `Enter` 키를 추가해야 실행됩니다. 사용자가 명령 문자열 끝에 `Enter`를 포함하도록 하거나 자동으로 추가하도록 설계합니다.
   - `executeInPane(paneId: string, command: string): void`
     1. `command`를 단일 문자열로 작성하고, `sendKeys` 호출 시 `[command, 'Enter']`를 전달합니다.
     2. 명령 실행 후 프로그램이 완료될 때까지 기다리지 않고 비동기로 처리할지, 출력이 필요할지에 따라 후속 `capturePane` 호출 여부를 정합니다.

6. **출력 캡처 함수**
   - `capturePane(paneId: string, startLine?: number, endLine?: number, escapeNonPrintable?: boolean, joinWrappedLines?: boolean): string`
     1. 기본적으로 `-p` 플래그를 사용합니다【261256137316099†L930-L943】.
     2. `startLine`과 `endLine` 값이 정의되면 `-S`와 `-E`를 지정하고, 음수 값일 경우 히스토리까지 포함합니다【261256137316099†L938-L943】.
     3. `escapeNonPrintable`이면 `-C`, 공백과 줄바꿈을 유지하려면 `-N` 또는 `-J` 플래그를 추가합니다【261256137316099†L947-L953】.
     4. 결과 문자열을 에이전트가 읽을 수 있는 형식으로 반환합니다. 필요하다면 줄 개행을 다른 구분 기호로 바꾸거나 JSON으로 인코딩합니다.

7. **상태 질의 함수**
   - `getServerInfo(): ServerInfo`
     1. `tmux display-message -p '#{version} #{server_pid} #{sessions}'` 등의 포맷을 이용하여 버전, 프로세스 ID, 세션 수를 가져옵니다.
   - `getPaneMetadata(paneId: string): PaneMeta`
     1. `tmux display-message -p -t paneId '#{pane_pid} #{pane_title} #{pane_tty}'` 등을 사용하여 패널 관련 메타데이터를 추출합니다.

8. **확인(prompt) 및 보안 기능 구현**
   - 파괴적 작업(`kill-*`, `reset`, `source-file` 등)을 호출할 때는 함수 인자에 `confirm` 또는 `force` 플래그를 사용하여 호출 여부를 제어합니다. 필요 시 에이전트가 사용자에게 “이 세션을 종료할까요?” 같은 확인 메시지를 보내고, 사용자의 응답을 기다립니다.
   - **명령 검증**: `sendKeys`나 `executeInPane`에 전달되는 명령을 화이트리스트 또는 정규식으로 검증하여 의도치 않은 시스템 명령 실행을 막습니다.
   - 비밀 데이터 출력 차단을 위해 `capturePane` 결과를 필터링하거나 민감한 패턴(예: 토큰, 키) 발견 시 마스킹합니다.

## 5. 에이전트 통합 및 상호작용 설계

1. **에이전트 호출 인터페이스 정의**
   - 스킬을 호출할 때 사용할 JSON 기반 API 또는 메소드 시그니처를 정의합니다. 예시:

     ```json
     {
       "action": "sendKeys",
       "paneId": "%3",
       "keys": ["python", "-c", "print('hello')"],
       "literal": false
     }
     ```

   - 반환 값은 성공 여부와 캡처한 출력, 오류 메시지 등을 포함합니다. 형식 일관성을 위해 결과 객체에 `status`, `data`, `error` 필드를 포함합니다.

2. **비동기 처리 모델 설계**
   - tmux 명령의 실행 시간이 다양한 만큼, 스킬 내부에서 비동기/동기 실행 모드를 지원합니다. 예를 들어 `executeInPane` 후 바로 `capturePane`을 호출하면 출력이 완전히 도착하기 전에 캡처될 수 있으므로, 일정 시간 지연 또는 출력 패턴에 대한 이벤트 리스너를 구현합니다.
   - Node.js는 `async/await`, Python은 `asyncio` 또는 `threading`, Rust는 `tokio`를 활용하여 비동기 명령 실행을 지원합니다.

3. **상태 관리 및 세션 추적**
   - 에이전트가 여러 세션과 패널을 동시에 관리해야 한다면, 세션 ID와 패널 ID를 매핑하여 추적하는 데이터 구조를 만듭니다. 세션이 종료되면 관련 패널 정보도 정리합니다.
   - 사용자별 작업 공간을 격리하기 위해 네임스페이스를 사용하고, 세션 이름에 사용자 ID나 작업 ID를 접두어로 붙여 중복을 피합니다.

4. **에이전트 대화 흐름 설계**
   - 예를 들어 Claude와 같은 대화형 AI가 tmux 스킬을 사용할 때, 사용자가 “새 Python REPL을 만들어줘”라고 요청하면 `createSession`, `createWindow`, `splitPane`을 호출하고, REPL을 실행한 후 첫 줄 출력을 `capturePane`으로 반환하는 등의 시나리오를 설계합니다.
   - 대화의 각 단계에서 에이전트가 어떤 스킬 함수를 호출해야 하는지, 언제 출력 캡처를 수행할지 등을 대화 템플릿으로 정의합니다.

## 6. 테스트 및 검증

1. **단위 테스트 작성**
   - 각 함수별로 정상 동작, 예외 처리, 엣지 케이스를 테스트합니다. 예를 들어 존재하지 않는 세션 이름으로 `killSession`을 호출했을 때 적절한 오류가 발생하는지 확인합니다.
   - 테스트 실행 시 실제 tmux 소켓을 사용하지만, 테스트가 끝나면 자동으로 세션을 정리하도록 `setup`과 `teardown`을 구현합니다.

2. **통합 테스트**
   - 실제 에이전트 흐름과 유사한 시나리오를 작성합니다. 예: 세션을 만들고, 새 윈도우를 추가하고, 패널을 분할한 뒤, `sendKeys`로 Python 명령을 실행하고, `capturePane`으로 결과를 읽는 등.
   - 원격 모드가 있다면 SSH 환경을 설정해 원격 호스트에서 tmux 명령이 실행되는지 검증합니다.

3. **성능 및 병목 분석**
   - 여러 세션을 동시에 생성하고 명령을 보내는 스트레스 테스트를 수행해, 에이전트가 병렬 작업을 처리할 수 있는지 확인합니다.
   - 출력 캡처에서 대량의 히스토리를 가져올 때 시간이 오래 걸리는지 측정하고, 필요한 경우 버퍼 제한이나 페이징 기능을 구현합니다.

4. **보안 테스트**
   - 명령 주입 공격을 시뮬레이션하여 `sendKeys` 입력 검증 로직이 작동하는지 확인합니다.
   - 세션 간 데이터 누수를 막기 위해 서로 다른 세션의 패널에 접근할 수 없는지 테스트합니다.
   - 비밀 정보(예: API 토큰, SSH 키)가 포함된 출력이 노출되지 않도록 필터링 로직을 검증합니다.

## 8. 운영 시 주의사항 및 모범 사례

1. **세션 네이밍 규칙 유지**
   - 세션과 윈도우 이름을 의미 있게 지정하여 나중에 관리하기 쉽게 합니다. 예를 들어 `<user>-<project>-<timestamp>` 형식을 사용합니다.
   - 세션 이름 충돌을 방지하기 위해 생성 전에 항상 `listSessions()`로 이름을 검사합니다.

2. **로그 및 감시**
   - 모든 명령 실행과 결과를 로그에 기록하고, 에이전트의 행동을 추적할 수 있도록 합니다. 특히 원격 서버에서 실행되는 경우 감사 로그를 중앙 서버에 전송합니다.
   - 로그에 비밀정보가 포함되지 않도록 필터링하고, 보관 기간과 접근 권한을 제한합니다.

3. **리소스 정리**
   - 사용하지 않는 세션이나 패널을 자동으로 종료하는 정책을 설정하여 리소스 낭비를 줄입니다. 예: 마지막 사용 시간 기준으로 일정 시간 경과 시 세션 종료.
   - 앱이나 서버가 재시작되면 잔존하는 tmux 세션을 탐지하여 필요한 경우 복구하거나 종료합니다.

4. **권한 관리**
   - 에이전트가 사용하는 시스템 계정에 최소 권한만 부여합니다. 파일 시스템 접근, 네트워크 접근 등을 세밀하게 제한하여 보안을 강화합니다.
   - 여러 사용자가 에이전트를 통해 동일한 서버에 접속하는 경우, 각 사용자별로 서로 다른 tmux 소켓 또는 네임스페이스를 사용하여 격리합니다.

5. **모니터링 및 알림**
   - tmux 서버 상태(세션 수, CPU/메모리 사용량)를 지속적으로 모니터링하고, 임계값을 넘을 때 운영자가 알림을 받을 수 있도록 설정합니다.
   - 에이전트가 비정상 종료되거나 세션이 예상치 않게 종료되면 자동으로 재시작하거나 경고를 보내는 로직을 구현합니다.

## 9. 확장 기능 고려 사항

1. **다중 사용자 및 협업 모드**
   - 여러 에이전트나 사용자가 동일 세션에 참여해야 하는 경우, 패널별 접근 제어와 출력 브로드캐스트 기능을 추가합니다.
   - 입력 충돌을 막기 위해 큐잉 또는 잠금 메커니즘을 도입하고, 어느 사용자가 어떤 명령을 실행했는지 기록합니다.

   - 웹 기반 대시보드나 IDE 플러그인에서 tmux 세션을 관리할 수 있도록 REST API나 WebSocket 인터페이스를 제공합니다.
   - 출력의 하이라이팅, 터미널 색상 재현, 명령 이력 검색 기능 등을 추가하여 사용성을 개선합니다.

3. **스크립트 및 자동화**
   - 반복적으로 사용되는 명령 시퀀스를 스크립트로 저장하고 재실행할 수 있는 기능을 제공합니다. 예를 들어, 특정 프로젝트의 개발 환경을 세팅하는 스크립트를 정의하여 클릭 한 번으로 세션과 윈도우, 패널을 구성합니다.

4. **버퍼 검색 및 데이터 추출**

   - `list-buffers`와 `show-buffer` 명령을 사용하여 tmux 내부 버퍼를 조작하는 기능도 제공할 수 있습니다.

5. **맞춤 레이아웃 및 복구**
   - 복잡한 윈도우/패널 구조를 사전에 정의하여 필요한 순간에 호출할 수 있게 합니다. 예를 들어 3×3 그리드, 왼쪽 코드 편집기/오른쪽 로그 창 등.
   - 에이전트가 작업 중 세션이 끊겼을 때 레이아웃과 환경을 복구하는 절차를 구현합니다.
