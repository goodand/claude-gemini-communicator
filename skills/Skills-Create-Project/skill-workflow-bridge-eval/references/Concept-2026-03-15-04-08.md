## 핵심 원칙
  자연어 출력은 결과(result)가 아니라 우선 주장(claim) 으로 취급해야 해.
  즉 다음처럼 처리해야 한다.

  1. raw_output는 그대로 보존
  2. 별도로 bridge_eval을 만든다
  3. bridge_eval이 통과해야만 다음 Skill로 넘긴다
  4. 미통과면 retry / reroute / evaluator-loop / stop 중 하나를 결정한다

  즉 구조는 이거다.

  - raw_output.md
  - bridge_eval.json
  - repair_prompt.md 또는 retry_spec.json
  - handoff_packet.json

  ———

  ## 자연어 출력 처리 방식

  ### 1. 출력 타입 먼저 분류

  각 Skill 출력은 최소 아래 중 하나로 분류해야 한다.

  - script_result
  - structured_json
  - natural_language
  - mixed

  자연어면 그 순간부터 평가 방식이 달라진다.

  ———

  ### 2. 자연어는 바로 handoff 금지

  자연어 출력은 다음 Skill의 입력으로 직접 사용하지 않고, 반드시 한 번 더 정규화해야 한다.

  중간 계층이 필요하다.

  - extract
  - grade
  - decide

  즉:

  1. 자연어에서 필요한 정보 추출
  2. 조건 충족 여부 평가
  3. 다음 실행 결정

  ———

  ### 3. 자연어용 평가 기준을 별도로 둬야 한다

  스크립트 출력은 exit code, stdout, 파일 생성 여부로 볼 수 있다.
  하지만 자연어는 아래처럼 봐야 한다.

  - 요구된 항목이 모두 포함됐는가
  - 모순이 없는가
  - 근거가 있는가
  - 다음 Skill이 사용할 수 있을 만큼 명확한가
  - 포맷이 handoff 가능 상태인가
  - 애매한 표현이 많은가
  - “했다고 말만 했는지”, 실제 산출물이 있는지

  ———

  ## 추천 처리 구조

  ### A. Raw 보존

  - raw_output.md

  여기엔 원문 그대로 저장한다.

  ### B. Extraction

  자연어에서 다음 필드를 뽑는다.

  - task_completion_claim
  - key_outputs
  - missing_items
  - open_questions
  - evidence
  - confidence
  - next_step_ready

  이건 extractor가 만든다.
  가능하면 JSON schema 강제.

  예:

  {
    "output_type": "natural_language",
    "task_completion_claim": false,
    "key_outputs": ["초안 작성", "리스크 2개 식별"],
    "missing_items": ["절대경로 없음", "체크리스트 미작성"],
    "open_questions": ["다음 Skill이 요구하는 JSON 포맷 미정"],
    "evidence": ["원문에 파일 경로 미포함"],
    "confidence": 0.74,
    "next_step_ready": false
  }

  ### C. Grading

  그 다음 evaluator가 본다.

  - 필수 조건 충족률
  - evidence 충분성
  - ambiguity 정도
  - handoff 가능성
  - 재시도 가치

  예:

  {
    "pass": false,
    "score": 0.62,
    "unmet_conditions": [
      "필수 출력 필드 누락",
      "다음 Skill 입력 포맷 불일치"
    ],
    "failure_type": "recoverable",
    "recommended_action": "retry"
  }

  ### D. Decision

  마지막으로 decision layer가 결정한다.

  - pass
  - retry
  - reroute
  - loop
  - stop

  ———

  ## 재실행 루프는 어떻게 해야 하나

  여기서 중요한 건 blind retry가 아니라 repair retry여야 한다는 점이야.

  즉 그냥 다시 돌리는 게 아니라, evaluator가 실패 이유를 구조화해서 다음 재실행 입력으로 넣어야 한다.

  ### retry 조건

  다음은 재실행 가능 실패다.

  - 필수 항목 누락
  - 형식 불일치
  - 근거 부족
  - 너무 모호함
  - 다음 Skill 입력으로 정규화 불가
  - self-contradiction 경미
  - confidence 낮음

  ### reroute 조건

  다음은 재실행보다 우회가 맞다.

  - 같은 실패가 2~3회 반복
  - 필요한 정보가 현재 Skill 능력 밖
  - 다른 Skill이 더 적합
  - 포맷 문제가 아니라 접근 방식 자체가 틀림

  ### stop 조건

  - unsafe
  - upstream artifact 없음
  - 핵심 전제 붕괴
  - retry로 회복 불가능

  ———

  ## 자연어 출력에서 제일 중요한 포인트

  ### 1. “완료했습니다”를 믿지 말 것

  자연어 출력은 자기보고식 completion claim이 많다.
  이건 성공 증거가 아니다.

  성공 판정은 반드시 아래로 해야 한다.

  - 실제 산출물 존재 여부
  - 필수 항목 충족 여부
  - 다음 Skill 입력 적합성
  - evidence 존재 여부

  ### 2. 다음 Skill에는 원문 전체가 아니라 “정제된 handoff”를 넘길 것

  다음 Skill 입력은 보통 이 3개 조합이 더 낫다.

  - normalized_summary
  - structured_extraction
  - decision / unmet_conditions

  즉 다음 Skill은 raw 자연어 전체보다, 정제된 packet을 받아야 한다.

  ## 추천 canonical artifact

  skill-workflow-bridge-eval에서는 이 4개를 기본으로 두는 게 좋다.

  1. raw_output.md
  2. bridge_eval.json
  3. retry_spec.json
  4. handoff_packet.json

  ### retry_spec.json

  {
    "retryable": true,
    "retry_count": 1,
    "max_retries": 3,
    "unmet_conditions": [
      "필수 섹션 누락",
      "근거 문장 없음"
    ],
    "repair_instructions": [
      "필수 섹션 4개를 모두 포함할 것",
      "각 주장마다 근거 1개 이상 붙일 것"
    ],
    "no_progress_signal": false
  }

  ### handoff_packet.json

  {
    "ready": false,
    "decision": "retry",
    "next_skill": null,
    "normalized_summary": "초안은 있으나 체크리스트와 절대경로가 누락됨",
    "key_outputs": ["초안 작성"],
    "missing_items": ["체크리스트", "절대경로"],
    "confidence": 0.62
  }

  ## 실제 의사결정 규칙 추천

  ### 규칙 1

  자연어 출력이면 무조건 extraction 단계 거치기

  ### 규칙 2

  next_step_ready=false면 직접 handoff 금지

  ### 규칙 3

  failure_type=recoverable이면 retry 우선

  ### 규칙 4

  같은 unmet condition 반복 2회면 reroute 검토

  ### 규칙 5

  max retry 초과면 loop 종료

  ———

  ## 한 줄 결론

  자연어 출력은 그대로 다음 Skill의 입력이 아니라, 평가와 정규화를 거친 뒤 handoff packet으로 변환해야 한다.
  그리고 조건 미충족 시 재실행 루프는 단순 재시도가 아니라, unmet condition 기반 repair retry로 설계해야 한다.
